Event-Stomming 하는 이유
: Actor -> 주체   /   Command -> 명령
: 지금까지는 Actor 와 Command 의 구분이 명확하지 않았음.
: 이걸 명확하게 하기 위해 사용.
========================================
Step 1. 도메인 이벤트 수집(Big Picture) (주황색)
(= 명령에 의해 발생되는 이벤트)
- 주황색 포스트잇
 : '전문가 이벤트'를 나타냄.
- 전문가 이벤트
 : 비즈니스 과정에서 발생한 중요한 사실 의미함.
 : 이 이벤트는 기술적으로 관련 있어야 하고, 과거에 발생한 일이어야 함. 
 : 즉, 단순 아이디어 혹은 추상적인 개념이 아닌 실제 시스템에서 발생한 사건이나 변화를 의미함. 
 : 그래서 포스트잇에 적는 동사는 항상 과거형으로 작성.

* 브레인 스토밍
 : 기존 도메인 이벤트에 대해 자유롭게 아이디어내는 시간. 생각나는 이벤트 포스트잇에 적어 붙이고 이 이벤트를 발생한 순서대로 정리하기.

1-1. 요구사항 명세를 바탕으로 발생할 수 있는 도메인 이벤트 모두 작성(view 는 작성 X)
   - 항상 과거형으로 작성(ex. 생성됨)

1-2. 1-1에서 나온 것들 시간의 흐름(왼->오)대로 정리.
   - 같은 선상에 있는거는 동일에 일어날 수 있는 일들.

1-3. 유비쿼터스 언어 맞추기. (= 동일한 언어 사용하기)
ex)  강좌, 강의의 시간 흐름을 정하기 모호할 때 강좌와 강의가 의미하는 바를 정의하여 팀원 모두 같은 의미로 사용하기.
-----------------------------------------------------------------------
Step 2. 커맨드(=명령) 정의 (파란색)
- 파란색 포스트잇 
 : 커맨드를 나타냄.

- 커맨드
 : 사용자가 시스템에 요청하는 행동이나 작업 의미. 
 : 시스템 비즈니스 로직에 따라 수행되며, 일반적으로 사용자가 시스템에 어떤 작업을 요청했을 때 발생. 
 : 각 커맨드는 특정한 결과를 초래하며, 해당 결과에 따라 도메인 이벤트 발생할 수 있음. 
 : 포스트잇에 적는 동사는 항상 현재형으로 작성.
* 브레인 스토밍
 : 커맨드 정의 과정은 시스템 요구사항을 명확히 하고, 사용자 행동을 이해하는 시간.
 : 각자 생가나는 커맨드 적어 붙이고, 이 커맨드들이 시스템 내에서 어떻게 작동할지 논의
 : 각 커맨드는 이벤트와 연결되어야 하며, 이 연결을 통해 시스템 흐름을 명확히 이해할 수 있도록 함.
- 문제점 (예시)
 : "결제 취소"와 "결제 실패"는 상황이 다름.
 : 결제 취소는 결제가 이미 성공한 상태에서 환불하는 것. 결제 실패는 결제 시도 자체가 실패한 것.
: 이 둘에 같은 이벤트를 사용하면 나중에 왜 수강이 취소됐는지 거부됐는지 추적할 때 헷갈림.
=> 1차 용어 정리 : 수강취소(환불로 인한 수강 상태 변경), 수강거부(결제 실패로 인한 수강거부) 
=> 2차 용어 정리 : 이벤트 스토밍 과정에서 불필요한 커맨드 존재 파악. (수강 포기, 수강 취소, 수강 거부, 환불)

Step 3.외부시스템 (핑크색)
: 외부시스템 은 현재시스템과 상호작용하거나 영향을 미치는 다른 시스템
- 핑크색 포스트잇
 : 외부시스템

- 외부시스템
 : 현재 시스템과 상호작용하거나 영향을 미치는 다른 시스템
 : 외부 시스템은 데이터 제공, 인증, 통신 등 다양한 기능을 수행하며, 내부 시스테과의 연계를 통해 비즈니스 프로세스 지원.
 : 이 시스템은 특정 API 호출, 데이터베이스, 서드파티 서비스 등 포함할 수 있음.

- 브레인스토밍
 : 외부 시스템 정의 과정은 시스템의 통합 요구사항을 명확히 하고, 서로 다른 시스템 간의 상호작용을 이해
 : 각자 생각나는 외부 시스템 적어 붙이고, 외부 시스템들이 내부 시스템과 어떻게 연결될지 논의
 : 각 외부 시스템은 커맨드 및 도메인 이벤트와 연결할 수 있으며, 이를 통해 시스템 간 흐름과 데이터 전송 과정 명확히 이해할 수 있음.
-----------------------------------------------------------------------
Step 4. 액터 정의 (노란색)
* 절대 액터 위주로 생각하지 말것❌ 커맨드 위주로 생각할 것⭐
- 노란색 포스트잇
 : 액터

- 액터
 : 시스템과 상호작용하는 사용자 또는 외부 시스템.
 : 시스템 기능을 사용하거나 영향을 미치는 주체 (인간, 사용자, 다른 시스템, 조직)
 : 시스템 요구사항 정의하는데 중요한 역할을 하며, 사용자의 행동과 요구 반영
  => 커맨드를 실행시키는 주체를 의미

* 브레인 스토밍
 : 시스템의 사용자와 그들의 요구사항을 명확히 하고, 시스템과의 상호작용 이해
 : 각자 생각나는 액터 적어 붙이고, 이 액터들이 시스템 내에서 어떻게 작용할지 논의
 : 각 애터는 커맨드 및 도메인 이벤트와 연결 가능, 이를 통해 사용자의 행동이 시스템에 미친영향 명확히 이해할 수 있도록 함.
-----------------------------------------------------------------------
Step 5. 정책 정의 (보라색)
- 보라색 포스트잇
 : 정책

- 정책
 : 시스템 내에서 특정 행동이나 결정이 어떻게 이루어져야 하는지 정의하는 원칙이나 규칙
 : 정책은 비즈니스 로직 지원하며, 시스템의 일관성과 안정성을 유지하는데 중요한 역할.

* 브레인스토밍
 : 시스템의 비즈니스 규칙과 요구사항을 명확히 하고, 사용자 행동과 시스템 간의 상호작용을 이해
 : 각자 생각나는 정책을 적어 포스트잇에 붙이고, 정책이 시스템 내 어떻게 적용될지 논의.
 : 각 정책은 커맨드 및 도메인 이벤트와 연결될 수 있으며, 정책이 사용자 행동에 미치는 여향을 명확히 이해할 수 있도록 함.

* 2차 용어 정리
- 이벤트 스토밍 과저에서 불필요한 커맨드 존재 파악.

중요⭐ 이벤트가 어떤 정책에 의해 발생할건지 작성.
정책정의서에 있는 내용을 여기에 반영함.

Step 6. 애그리거트 후보 도출 (진한 노랑색[진한 주황색])
* 애그리거트란
 : 하나의 트랜잭션에서 함께 변경되어야 하는 객체 집합
 : 도메인규칙(invariant)을 깨지 않도록  보장해야 하는 최소 단위

- 진한 노랑색 포스트잇
 : 애그리거트

- 애그리거트
 : 도메인 내에서 관련된 데이터와 비즈니스 로직을 캡슐화하는 집합체
 : 특정 비즈니스 규칙을 유지하며, 일관성을 보장하는 단위로, 루트 엔티티를 통해 외부와 상호작용함.

* 브레인스토밍
 : 시스템의 구조와 비즈니스 로직을 명확히 하고, 데이터 간 관계를 이해하는 브레인스토밍 시간.
 : 각자 생각나는 애그리거트 적어 붙이기, 이 애그리거트가 시스템 내 어떻게 작동할지 논의
 : 각 애그리거트는 명령 및 도메인 이벤트와 연결될 수 있으며, 이를 통해 애그리거트의 상태 변화가 시스템에 미치는 영황을 명확히 이해.

* 애그리거트의 정의(Aggregate Definition) 도출 과정
 1. 사고의 출발점 : 불변식(invariant) 중심 사고
- 모델 분리 시 첫 질문. "어떤 비즈니스 규칙이 깨지면 안되는가?" / "그 규칙을 지키려면 어떤 객체들이 항상 함께 바뀌어야 하는가?"
- 개념적 기준(모델&의미)
 : 언어(Meaning) - 같은 언어 체계인가? 다르면 분리
 : 책임(Responsibility) - 하나의 정책/규칙으로 묶이는가? 다르면 분리
 : 역할(Role) - 서로 다른 역할의 주체가 관리하는가? 다르면 분리
 : 주기(Lifecycle) - 생성~삭제 흐름이 동일한가? 다르면 분리

⭐중요⭐
앤티티, 테이블임.

Step 7. 바운디드 컨텍스트 정의 (경계선, 관계선)
모든 참가자는 애그리거트 그룹을 기준으로 논의하며 보드 위 직접 경계선과 관계선을 그린다.
1. 경계선과 관계선의 의미
 : 경계선은 바운디드 컨텍스트(Bounded Context)를 나타낸다.
   - 바운디드 컨텍스트란. 특정 도메인 모델과 유비쿼터스 언어가 일관된 의미를 갖는 명시적인 경계이다.
   - 다음 중 하나라도 다르면 별도의 BC가 되어야 한다.
     1) 용어의 의미가 다른다. 
         ex) 강의(Leacture) 가 콘텐츠 제작 맥락에서는 비디오 자산이고, 수강 맥락에서는 시청 가능한 단위로 쓰면, BC 분리 필요
     2) 정책과 규칙의 주체가 다르다.
         ex) 결제 정책은 재무팀/PG사 규칙, 수강 정책은 교육운영팀 규칙.
     3) 데이터 일관성 요구가 다른다.
         즉시 일관성이 필요한 곳과 지연 일관성이 허용되는 곳
     4) 개발 사이클/변경 속도가 다르다
         콘텐츠 업로드 로직과 결제 

* 브레인스토밍
 : 바운디드 컨텍스트 정의 과정은 애그리게이트 그룹들을 묶어 더 큰 논리적 경계를 확정하고, 시스템의 전체 다키텍처를 조망하는 시간이다.
 : 참가자들은 각 애그리게이트 그룹의 언어적 차이를 기준으로 경계선을 그리고 바운디드 컨텍스트의 이름을 부여한다.

Step 8. 컨텍스트 맵 정의
* 바운디드 컨텍스트 정의 및 컨텍스트 맵핑
 : 모든 참가자는 애그리거트 그룹을 기준으로 논의하며 보드 위 직접 경계선과 관계선을 그린다.

1. 경계선과 관계선의 의미
  - 경계선은 바운디드 컨텍스트를 나타낸다. 바운디드 컨텍스트란 특정 도메인 모델과 유비쿼터스 언어가 일관된 의미를 갖는 명시적인 경계이다.
  - 다음 중 하나라도 다르면 별도의 BC가 되어야 한다.
    1) 용어의 의미가 다른다.
       ex) 강의가 콘텐츠 제작 맥락에서는 비디오 자산이고, 수강 맥락에서는 시청 가능한 단위로 쓰이면 BC 분리 필요
    2) 정책과 규칙의 주체가 다르다.
       ex) 결제 정책은 재무팀/PG 사 규칙, 수강 정책은 교육운영팀 규칙.
    3) 데이터 일관성 요구가 다르다.
       즉시 일관성이 필요한 곳과 지연 일관성이 허용되는 곳.
    4) 개발 사이클/변경 속도가 다르다.
       콘텐츠 업로드 로직과 결제 모듈을 릴리즈 주기가 완전히 다름.

* 브레인 스토밍 과정
 : 바운디드 컨텐스트 정의 과정은 애그리게이트 그룹들을 묶어 더 큰 논리적 경계를 확정하고, 시스템의 전체 아키텍처를 조망하는 시간이다.
 : 참가자들은 각 애그리게이트 그룹의 언어적 차이를 기준으로 경계선을 그리고 바운디드 컨텍스트의 이름을 부여한다.
